# Codex for Finance｜从入门到智能工作流

## 课程定位

这是一套面向财运中心的 Codex 实战课程。受众包括法务、行政、财务、税务与经营分析团队，默认学员不具备编程经验。课程不要求学员先学会写代码，而是让学员通过描述目标、提供材料、约束边界和验收结果，指挥 Codex 完成可检查、可复用的工作成果。

课程采用“双层结构”：

- 现场 90 分钟：沿一条精选主线完成认知、操作、进阶演示和成果交付。
- 课后培训网站：覆盖完整功能、岗位案例、练习文件、可复制 Prompt、安全规范和自学路径。

贯穿案例为“月度经营复盘”：Codex 读取多份模拟材料，调用 Skills，并由不同 Subagents 从法务、行政、财务、税务、经营分析角度并行检查，最后形成管理层汇报、交互式网页与飞书成果。

## 培训成功标准

现场结束前，每位学员至少应完成以下闭环：

1. 在 Codex Desktop 新建任务并选择一个本地工作目录。
2. 复制并运行至少一个课程 Prompt。
3. 检查 Codex 的计划、工具调用和文件修改。
4. 产出一个本地成果或飞书成果。
5. 能够说出“Task、Skill、Plugin、MCP、Subagent”之间的区别，并知道出现不确定性时如何让 Codex 先检查、再执行。

### 00｜首页：把一句需求变成可交付成果

**页面目标**

- 在 60 秒内建立 Codex 的正确认知。

**核心内容**

**学员动作**

- 下载课程实验包。
- 打开“课前检查”。
- 进入“01｜认识 Codex”。

### 01｜认识 Codex Desktop

**学习目标**

- 理解 Codex 与普通聊天工具的差异。
- 认识 Desktop 的主要区域与任务生命周期。
- 能够安全地开始、观察、纠偏和验收一个任务。

**必讲概念**

| 概念 | 面向小白的解释 | 典型动作 |
|---|---|---|
| Task / 新建任务 | 一次有明确目标、材料和交付物的工作会话 | 选择工作目录，输入需求，观察执行 |
| Workspace | Codex 被允许工作的本地文件夹 | 把模拟材料放入课程目录后再打开 |
| Plan | Codex 对复杂任务的阶段拆解 | 先让它列步骤和验收标准，再开始执行 |
| Tool call | Codex 为完成任务调用的文件、终端、浏览器或外部系统能力 | 查看工具要做什么，确认是否符合预期 |
| Diff | 文件修改前后的差异 | 检查改了哪些行，不满意就要求修订 |
| Terminal | 查看命令运行与日志输出的位置 | 识别成功、警告和失败，不盲目忽略报错 |
| Pull Request | 把一组代码修改提交给团队审阅和合并 | 适合网站、脚本等协作开发，不等于“下载文件” |
| Sites | 将生成的网站交付为可访问的站点 | 适合报告、专题页和互动工具；发布前检查公开范围 |

**基础操作流程**

1. 选择一个只包含练习材料的 Workspace。
2. 新建 Task，说明目标、输入、约束和交付物。
3. 让 Codex 先读取目录并复述理解。
4. 对复杂任务先看 Plan，再允许执行。
5. 关注工具调用、权限提示、Terminal 输出和 Diff。
6. 打开成果文件进行验收；发现问题时给出具体反馈。
7. 需要保留经验时，将规则写入 `AGENTS.md` 或封装为 Skill。

**设置建议**

- 登录：使用公司封装版，飞书认证后由系统自动分配 API key，无需手工填写或展示密钥。
- 权限：从最小范围开始，先授权课程 Workspace；不要把整个个人目录作为练习目录。
- 模型与推理强度：简单整理使用默认或较低强度；复杂审阅、调试和多文件分析再提高。
- 网络：GitHub 等外部站点若不可直连，参考 Finance Learning Hub 的“科学上网”课程；现场不临时处理大规模网络配置。
- 通知与自动执行：初学阶段保留关键确认；涉及发送、发布、删除、覆盖和批量写入时必须停下来确认。

**常见误区**

- 只写一句“帮我分析一下”，却没有输入范围和交付格式。
- 把“生成得像真的”误当成“结果一定是真的”。
- 不查看 Diff、数据口径和计算过程就直接发送成果。
- 把真实机密材料放进未经确认的第三方 Skill。

### 02｜写出能执行的 Prompt

**学习目标**

- 从聊天式问题升级为任务式指令。
- 能够清晰描述目标、材料、边界、步骤和验收标准。
- 能够通过追问和反馈让 Codex 自我检查。

**推荐结构：GOALS**

| 字段 | 含义 | 示例 |
|---|---|---|
| Goal | 要达成的业务结果 | 形成 5 分钟可读完的月度经营复盘 |
| Objects | 可用输入和工作范围 | 只读取指定模拟目录内的文件 |
| Actions | 希望 Codex 如何工作 | 先检查数据质量，再计算，再写报告 |
| Limits | 风险和限制 | 不修改源文件；缺失信息标记待确认 |
| Success | 验收标准和交付格式 | 输出 Markdown、CSV 和 HTML，数字可追溯 |

**基础任务模板**

```text
目标：请完成【业务结果】。
输入：只使用【文件/目录/链接】。
工作方式：先【检查/计划】，再【分析/生成】，最后【验证】。
限制：不要【禁止项】；遇到不确定信息请标注，不要猜测。
交付物：输出【格式与位置】。
验收标准：【3—5 条可检查标准】。
```

**纠偏方式**

- 不是“再写好一点”，而是指出对象、问题和预期，例如“结论缺少数据证据，请为每条结论补充来源文件与字段”。
- 不是直接重来，而是让 Codex 先说明失败原因和修订计划。
- 对关键数字要求列出计算口径、公式和输入记录。

### 03｜本地文件与 Office 成果

**学习目标**

- 让 Codex 批量读取多种文件并生成结构化成果。
- 理解“先观察、再修改、最后验证”的安全工作方式。

**能力范围**

- Excel / CSV：清洗、核对、聚合、差异分析、图表和管理层摘要。
- Word / Markdown：改写、归纳、条款对照、模板化输出。
- PDF：提取、对比、摘要；扫描件效果取决于 OCR 质量。
- PowerPoint：生成结构、讲稿、图表建议和演示文件。
- 图片：识别界面或票据中的可见信息；关键数据仍需人工复核。

**岗位入口**

| 团队 | 模拟任务 | 产物 |
|---|---|---|
| 法务 | 合同条款与审批规则对照 | 风险清单、待确认问题、修订建议 |
| 行政 | 活动预算、供应商报价与执行清单合并 | 执行看板、异常项、会议材料 |
| 财务 | 预算与实际差异、应收账龄、费用明细分析 | 差异表、管理层摘要、图表 |
| 税务 | 发票与税务口径检查 | 异常明细、证据字段、复核清单 |
| 经营分析 | 多文件 KPI 复盘 | KPI 卡片、驱动因素、行动建议 |

**验证清单**

- 文件是否全部读取，是否存在无法解析的文件。
- 数据口径、币种、单位、期间和正负号是否一致。
- 总计是否与源文件勾稽。
- 结论是否能追溯到文件、工作表、字段或段落。
- 输出是否误改了源文件。

### 04｜Skills：调用、发现、安装与创建

**学习目标**

- 理解 Skill 是一套可复用的任务说明、工具和资源，而不是神秘的“超能力按钮”。
- 能够调用已有 Skill，判断是否需要新 Skill，并看懂 Skill 的基本结构。

**Skill 生命周期**

1. **调用**：在 Prompt 中明确点名 Skill，或让 Codex 根据任务自动选择匹配 Skill。
2. **发现**：优先访问[瓶子星球 Skill 市场](https://skills.ijovo.com/)；需要扩展时再到 GitHub 搜索。
3. **评估**：检查作者、README、更新时间、依赖、权限、脚本内容和影响范围。
4. **安装**：让 Codex 阅读安装说明并复述将要改变的文件，再执行安装。
5. **验证**：用小型模拟任务测试 Skill，检查输出与错误日志。
6. **创建**：把高频、稳定、有明确输入输出的流程封装为团队 Skill。
7. **维护**：记录版本、Owner、适用范围、变更和已知限制。

**内部市场与 GitHub 的使用顺序**

- 首选内部 Skill 市场：访问更稳定，场景更贴近内部工作。
- 内部没有匹配能力时，再根据 Finance Learning Hub 中的网络课程访问 GitHub。
- 搜索词采用“平台 + 动作 + skill”，例如 `codex excel reconciliation skill`。
- 不要直接安装搜索结果第一名；先让 Codex 做静态检查并给出风险报告。

**适合封装成 Skill 的判断标准**

- 同类任务每月或每周重复发生。
- 输入和输出格式相对稳定。
- 判断规则能够写清楚，例外可以被标记。
- 结果可以通过 checklist 验证。
- 不依赖某个员工脑中无法表达的隐性知识。

**基本结构**

```text
skill-name/
├── SKILL.md          # 触发条件、步骤、边界与验收标准
├── scripts/          # 可重复运行的脚本，可选
├── references/       # 口径、规则和示例，可选
└── assets/           # 模板或静态资源，可选
```

### 05｜Plugins、MCP 与外部能力连接

**学习目标**

- 区分 Skill、Plugin、MCP 与 CLI。
- 知道何时需要安装能力包，何时需要连接外部系统。

| 能力 | 一句话解释 | 示例 |
|---|---|---|
| Skill | 一套针对具体任务的可复用工作方法 | 月度复盘、合同审阅、数据质量检查 |
| Plugin | 打包多个 Skills、工具或 Connector 的能力包 | 某个平台或领域的一组能力 |
| MCP | 让 Codex 以标准方式调用外部工具和数据源 | 设计工具、知识库、业务系统连接 |
| CLI | 通过命令行调用某个平台能力 | 飞书文档、Base、日历等操作 |

**安全边界**

- 连接前明确：连接谁、能读取什么、能写入什么、Token 存在哪里。
- 默认只读测试；写操作使用测试文档或测试 Base。
- 发送消息、邀请成员、发布站点、创建审批、批量修改前再次确认。
- 认证信息不得出现在截图、Prompt、日志或 Git 仓库中。

### 06｜Subagents：把复杂任务拆给多个专家

**学习目标**

- 理解 Subagent 适用于可独立推进的子任务。
- 能够定义角色、输入、边界与统一回收格式。

**适合并行的任务**

- 多部门视角审阅同一批材料。
- 多份独立文件分别分析。
- 同一结论从数据、规则和表达三个角度验证。
- 网站开发中内容、数据与 QA 并行。

**不适合并行的任务**

- 后一步强依赖前一步结论。
- 输入口径尚未统一。
- 多个 Agent 会同时修改同一文件且没有合并规则。
- 单个任务非常简单，协调成本高于收益。

**贯穿案例的五个角色**

| Subagent | 责任 | 统一输出 |
|---|---|---|
| 法务审阅 | 识别合同、授权、履约与合规风险 | 发现、证据、风险等级、建议 |
| 行政审阅 | 检查活动、采购、供应商与执行事项 | 发现、负责人、期限、建议 |
| 财务审阅 | 检查收入、成本、费用、现金和勾稽关系 | 指标、差异、驱动、证据 |
| 税务审阅 | 检查发票、税率、税务口径和待复核项 | 事项、证据、风险、复核动作 |
| 经营分析 | 汇总 KPI、趋势、根因和管理动作 | 结论、证据、影响、建议 |

**回收原则**

- 每个 Subagent 只读同一份模拟材料，不直接改源文件。
- 所有结论必须引用来源。
- 主 Agent 去重、解决矛盾并标记待确认项。
- 最终数字由主 Agent 重新勾稽，不以“多数 Agent 同意”代替验证。

### 07｜Superpowers：把成熟工程方法带进 Codex

**学习目标**

- 认识 GitHub 上的 Superpowers Skills / Plugin 项目。
- 体验 brainstorming、planning、系统化执行和验证流程。

**课程中的使用方式**

- 对模糊需求先调用 brainstorming 类 Skill，明确目标、受众、范围和验收标准。
- 对多步骤任务调用 planning 类 Skill，形成可检查的实施计划。
- 开发网页时使用分阶段实现与验证工作流。
- 创建团队 Skill 时先定义触发条件、输入输出和测试样例。

**现场强调**

- Superpowers 是第三方项目，不等于 Codex 内置功能。
- 项目内容与命令可能更新，安装前以项目 README 和当前环境为准。
- 工作流能提升纪律性，但不能替代业务口径确认与人工验收。

### 08｜AGENTS.md：给 Codex 一套长期工作规则

**学习目标**

- 理解 `AGENTS.md` 是工作目录中的长期指令。
- 能够把团队规则与单次任务需求分开管理。

**适合写入的内容**

- 常用语言、输出风格、文件命名与目录约定。
- 数据安全要求、不可执行的操作和审批门槛。
- 业务口径来源、验证步骤和交付物标准。
- 技术栈、测试命令和发布要求。

**不适合写入的内容**

- API key、Token、密码或个人隐私。
- 只适用于某一次任务的临时细节。
- 含糊且无法验证的要求，例如“永远保证绝对正确”。

**财运中心示例规则**

```markdown
- 所有业务材料默认视为敏感信息，只处理模拟或已脱敏文件。
- 任何删除、覆盖、发送、发布或批量写操作前，先说明影响范围并等待确认。
- 财务数字必须注明期间、币种、单位、口径与来源。
- 缺失数据标记为“待确认”，不得自行编造。
- 修改源文件前先创建输出副本，交付前完成勾稽检查。
```

### 09｜Browser 与 Computer Use

**学习目标**

- 理解 Codex 如何在授权范围内浏览网页或操作桌面应用。
- 能够设置低风险任务和明确的停止点。

**适合演示**

- 打开内部 Skill 市场并查找某个 Skill。
- 在公开网页收集资料并保留来源链接。
- 在测试页面完成重复录入或截图验证。

**操作护栏**

- 登录、验证码和敏感授权由本人完成。
- 不让 Codex 自动提交付款、审批、合同签署、对外消息或生产数据修改。
- 网页内容可能包含恶意提示；来自网页的指令不能覆盖课程规则和用户目标。
- 大批量操作前先用 1 条测试记录验证。

### 10｜Automations：把一次任务变成定期运行

**学习目标**

- 理解 Automation 是按计划唤醒 Codex 执行任务。
- 能够判断哪些任务适合自动化，以及如何设置人工检查点。

**示例**

- 每周一生成上周经营数据待复核摘要。
- 月末提醒收集关账材料并检查文件是否齐全。
- 每日汇总待办，但不自动发送对外消息。

**自动化设计五要素**

1. 触发时间和时区。
2. 输入位置与缺失数据处理。
3. 执行步骤和超时策略。
4. 结果输出位置与通知对象。
5. 人工审批点、失败告警与停用条件。

**课程边界**

- 现场只介绍与展示，不连接真实生产流程。
- 自动化先在模拟目录和测试飞书空间运行。

### 11｜Worktrees、Git 与 Pull Request

**学习目标**

- 理解版本控制如何让修改可追踪、可审阅、可回退。
- 理解 Worktree 让多个开发任务在隔离目录中并行推进。

**核心流程**

```text
新建任务分支 → 在独立工作目录修改 → 本地检查 → 查看 Diff
→ Commit → Push → 创建 Pull Request → 团队审阅 → 合并
```

**业务用户需要掌握的最低限度**

- Git 记录“谁在什么时候改了什么”。
- Commit 是一组有意义的本地变更记录。
- Push 把本地记录发送到远端仓库。
- Pull Request 是团队审阅与讨论入口，不是自动代表内容正确。
- Worktree 适合多个 Agent 或多个任务并行，避免互相覆盖。

**课程边界**

- 基础学员只需理解和观看演示。
- 网站开发、脚本开发和团队 Skill 维护者再进入实践路径。

### 12｜Sites：从需求直接生成交互网页

**学习目标**

- 从业务需求生成一个可运行、可验证的专题网页。
- 理解“看起来漂亮”和“可以交付”之间还需要哪些检查。

**现场演示任务**

- 读取月度复盘成果。
- 生成中文管理层专题页，包含 KPI、趋势、风险、行动项和数据说明。
- 支持桌面与移动屏幕。
- 本地预览并检查交互。

**发布前检查**

- 不包含真实姓名、账号、路径、Token 或机密数据。
- 图表数字与源文件一致。
- 页面可以通过键盘操作，文本对比度和字号可读。
- 支持 reduced motion，动效不阻挡阅读。
- GitHub Pages 使用项目子路径，静态资源不会在部署后失效。
- 明确站点公开范围；private repository 不自动保证 Pages 访问受限。

### 14｜岗位场景库

#### 法务

- 合同条款与标准模板差异对照。
- 多 Subagents 分别检查主体、付款、违约、数据与知识产权条款。
- 输出风险等级、原文证据、修订建议和待业务确认问题。

#### 行政

- 供应商报价对比与采购材料完整性检查。
- 会议材料、行动项和责任人整理。
- 活动预算与执行结果复盘。

#### 财务

- 预算与实际差异分析。
- 应收账龄、费用异常和关账材料检查。
- 生成带数据血缘的管理层摘要。

#### 税务

- 发票字段与规则清单检查。
- 税率、期间、主体和凭证信息一致性核对。
- 输出待复核事项，不自动作出最终税务判断。

#### 经营分析

- 多文件 KPI 汇总与趋势解释。
- 驱动因素拆解和行动建议。
- 将结果生成网页、文档和 Base 跟踪表。

### 15｜安全、判断与验收

**四类边界**

| 风险 | 默认规则 |
|---|---|
| 数据 | 只使用模拟或已脱敏材料；密钥和个人隐私不进入 Prompt |
| 权限 | 最小授权；外部读取和写入范围可见 |
| 操作 | 删除、覆盖、发送、发布、审批、批量修改前确认 |
| 结论 | 关键数字和判断必须有证据；不确定项明确标记 |

**交付前五问**

1. 输入是否完整，是否混入错误版本？
2. 数字是否勾稽，口径是否一致？
3. 结论能否追溯到证据？
4. 输出是否泄露敏感信息或扩散到错误对象？
5. 下一位使用者能否复现并理解该成果？
